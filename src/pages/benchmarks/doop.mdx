# DOOP points-to

<p className="bench-lede">
How fast <FL/> runs the DOOP Java points-to analyses, compared with Soufflé.

  <dt>Engines</dt>

  <dd>24 context-sensitive points-to analyses × 6 DaCapo Java programs (luindex, eclipse, batik, h2o, xalan, spring).</dd>
  <dt>Measured</dt>
  <dd>Run time to fixpoint via <code>.printsize</code> (no output serialization) and peak memory (RSS). Median of 3 runs, or a single run when it takes 60 s or more. Each run is capped at 1000 s and 190 GB; past either, it counts as not finished. The first three analyses ran earlier, with median of 3 throughout and an 1800 s cap; none of their finished results took over 900 s.</dd>
  <dt>Platform</dt>
  <dd>AMD EPYC 7V13 (Milan), 24 cores, 216 GB RAM, facts on ext4. Both engines run at 16 threads.</dd>

The two 2-call-site-sensitive analyses need more memory than this machine has: <FL/> and Soufflé without hand-tuning hit the 190 GB cap, and hand-tuned Soufflé hit the 1000 s limit. In an earlier 32-thread sweep on a 503 GB machine with an 1800 s limit, <FL/> finished both on luindex, eclipse and xalan (471–946 s, 357–419 GB) and Soufflé did not. That sweep also had <FL/> finishing 2-object-sensitive+2-heap on spring (1277 s) and selective-2-object-sensitive+heap on h2o (904 s); here both hit the 1000 s limit. Soufflé finished neither in either sweep.
